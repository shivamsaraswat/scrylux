# Phase 3 Milestone 4: manual extraction runs (FR-084, SC-002)

Until the eval harness arrives in Milestone 7, this file stands in for the gate of Principle II. Each run drove the built app and worker (`apps/api/dist`) against the test database and the sample `evals/samples/scrylux/design.md` (31,093 characters, 19 chunks, read whole at the default `EXTRACTION_CONTEXT_CHARS=36000`): upload, wait until ready, start an extraction through `POST /threat-models/{id}/extraction`, wait for the job, read the draft. Settings other than those named are the defaults. Keys were taken from the maintainer's shell and were never written to a file or printed.

Host for both runs: the maintainer's development Mac (Apple silicon, macOS 27.2), not the smallest host the deployment guide names and not a GPU server. Run on 2026-11-08.

## Run 1: hosted, passes

| Field | Value |
|---|---|
| Provider, model | Gemini, `gemini-3.6-flash` (embeddings: Gemini, `gemini-embedding-2`) |
| `LLM_TIMEOUT` | 5m |
| Valid draft | **Yes**, on the first attempt |

| Items | 20 elements (4 processes, 2 data stores, 2 external entities, 3 trust boundaries, 9 data flows), 6 assets, 6 assumptions; every element carries 1 checked citation, 20 in all |
| Usage | 1 request, 8,606 input tokens, 11,230 output tokens (thinking tokens included, against `EXTRACTION_MAX_OUTPUT_TOKENS` 12000) |
| Cost | $0.0486 (price list) |

The draft names the browser app, the API, the worker, the extraction child, PostgreSQL, file storage, the provider and the three boundaries the document describes, with the credentials, secrets and stored text as assets.

**Two defects found by this run and fixed in the same change**, which no simulated test could show:

- **Gemini refused the answer's JSON Schema** with `400 INVALID_ARGUMENT` and no detail, 7 seconds in, before any token. Bisected against the provider: the schema's `maxItems` was the cause (arrays of 40 and 15 refused, 10 accepted). `packages/llm/src/schema.ts` now moves `maxItems` into the field's description for Gemini, as it already does for Anthropic and Bedrock; zod stays the only judge of validity. `packages/llm/test/schema.test.ts` holds it.
- **An extraction's failure hint named `EMBEDDING_MODEL`** for a generation failure, because every job that was not a provider check took the embedding prefix. An extraction now names `LLM_MODEL`, unless it failed in its first step, where it may have called the embedding provider to choose chunks (`apps/api/test/contract/v1/extraction.test.ts`).

Watch: 11,230 output tokens is 94% of the default output limit, because this model's thinking tokens count. A larger design document or a more verbose model may need `EXTRACTION_MAX_OUTPUT_TOKENS` raised; the failure then says so.

## Decision: the local run is waived (2026-11-09)

The maintainer's hardware cannot run a local model larger than the 3B `llama3.2`, so the pre-release run with a local model (quickstart §3, SC-002's local half) is **not made** and the maintainer chose to skip it. The hosted run above stands as this milestone's recorded run. **SC-002 is therefore verified for a hosted model only.** Principle II, FR-084, SC-002 and research #16 were reworded the same day to "a hosted model and, where the maintainer has hardware for one, a local model", so this record and the constitution agree; the constitution stays at 1.17.0. No default was changed, and `docs/ai-providers.md` says no local model has been verified. A local model's extraction is covered by tests with simulated answers, by the retry and failure paths, and by Run 2 below, which shows a model that is too small, or given too small a context, fails cleanly with a hint and stores nothing.
