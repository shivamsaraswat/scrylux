## Summary

Phase 2, Milestone 7 (dogfood, `specs/phase-2/milestone-7-dogfood/`): **Specter's own threat model, built in Specter, committed to the repository**, with checks that keep it true.

- **`docs/threat-model/`** holds the model as a Specter file (`threat-model.specter.json`), the Markdown report Specter writes for it (`report.md`) and a `README.md`. The files are the unedited output of Specter's own export.
- **41 elements** (4 trust boundaries, 4 external entities, 10 processes, 2 data stores, 21 data flows), **255 threats** (237 generated by the shipped rules, every one decided; 18 added by hand for the risks the rules cannot derive, 5 of them threats of the whole model for the CI/CD pipeline) and **188 mitigations** (98 verified by a named test, 57 implemented, 33 proposed, each proposed one a remedy that `plan.md`, a phase or a guide schedules). By status: 32 open, 63 mitigated, 92 accepted, 68 not applicable.
- **Checks** (`apps/api/test/dogfood/`, 78 tests) run in the required `test` check: the committed files are valid, are what Specter writes, import with nothing left out and export back to the same content, have no ties an id would have to break, and hold no secret pattern; the report is the one Specter builds for the file; "Generate threats" on the import flags nothing **stale** (blocks) and would add nothing (**warns** when a rule was added).
- **Documents**: the front-page README, `CONTRIBUTING.md`, the pull request template and `docs/ci.md` point to it; the constitution (1.12.0) says the Threat Model section governs and that the model is updated in the same change.

No product code, no endpoint, no table, no migration and no dependency changed (spec FR-022).

## How this satisfies Principles I–VI

See the [constitution](https://github.com/shivamsaraswat/specter/blob/main/.specify/memory/constitution.md).

| Principle | How |
|---|---|
| **I. Secure coding** | No new input path, SQL or credential. The tests read two committed files and call existing authenticated operations. A pattern check scans the three files for credentials, email and IP addresses, cloud account identifiers and tokens on every pull request. |
| **II. Test-first** | The pure checks were written red (`checks.test.ts`, module missing), then implemented; the database-backed cases red (`operations.ts` missing), then implemented; `threat-model.test.ts` was run red with no files present (the message names the fix) before any file was authored, and went green when they were committed. Every check is shown to fail on a broken input, in the tests and on the real files (below). |
| **III. Simplicity** | No dependency, no abstraction, no later-phase content. The authoring scripts were throwaway and are not committed: a committed script would be a second source of truth. |
| **IV. Maintainability** | No environment variable and no log line. The secret patterns are a data module with no logic (`patterns.ts`), each with a sample that must match and a near-miss that must not. Every failure names the file, the check and the fix. |
| **V. Least privilege / Threat Model** | No new endpoint, asset or trust boundary. The model discloses nothing the constitution does not already publish. Principle V is extended (see below). |
| **VI. AI output is a draft** | No AI feature. The model holds no AI-origin threat (a check refuses one) and nothing of Phase 3 or later. |
