# Tasks: Release v0.1

**Input**: Design documents from `/specs/phase-2/milestone-8-release-v0-1/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/release-pipeline.md,
contracts/release-artifacts.md, contracts/checks.md, quickstart.md

**Tests**: Required.

- Constitution Principle II requires a failing test before each new behaviour. The behaviour this
  milestone adds is mostly checks and decision logic, so every script and check has its test task first,
  and that test **MUST be run and seen failing** before the task that makes it pass.
- Exceptions, each said where it occurs: the Definition of Done test (T031, T032) exercises behaviour that
  already exists, so it is expected to pass at once, and a defect it finds is fixed with a test that
  fails first (FR-040); the demo and threat-model files are content, held by tests written before them
  (T023, T024 for the demo; Milestone 7's checks, run at T046, for the model).

**Organization**: by user story, **not in priority order**, because dependencies override it.

- **Phase 1 (Setup) and Phase 2 (Foundational)** hold the spikes, the repository settings and the pure
  code (versions, changelog extraction, release notes) that the stories share.
- **US1 (P1)** is the pipeline and the image; **US2 (P1)** is the quickstart that uses them; **US3 (P1)**
  is the demo. Build them in that order.
- **US5 (P2)** and **US6 (P2)** need nothing from US2 and US3 and can follow in either order.
- **US4 (P2)** needs the demo (screenshots) and the changelog (links), so it comes after US3 and US6.
- **US7 (P2)** comes last of the stories: the threats it records name the tests and documents the
  earlier phases create.
- **Two pull requests, not one.** Some edits state that a release exists: the README's status, quickstart
  and demo download, its roadmap's ✅, `SECURITY.md`'s supported versions, and `plan.md`'s Phase 2 and
  Name. If they were merged with the pipeline, the front page would describe a release for as long as the
  rehearsal takes, and for good if the name check finds a collision. They are marked **[RELEASE-FACING]**,
  are **never committed on the first pull request's branch**: each is written, checked, saved as a patch in
  `SCRATCH` (`git diff <file> > SCRATCH/release-facing-<task>.patch`, then `git checkout <file>`) and applied
  at T052 on a second branch, whose pull request is merged right before the final tag (T060). Everything else
  is the first pull request.
- **Phase 10 (Polish)** closes the first pull request. **Phase 11 (Release)** happens **after the merge**, by the
  maintainer, because it needs the merged pipeline, the repository's settings and a registry.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task).
- **[Story]**: US1 to US7, from spec.md. Setup, Foundational, Polish and Release tasks have none.
- **[RELEASE-FACING]**: part of the second pull request (see Organization): saved as a patch in `SCRATCH`, not committed on the first branch.
- **[MAINTAINER]**: needs the repository owner's access (settings, a registry, a second machine, a
  decision). Nothing else in this list changes a setting, pushes a tag or publishes anything.

## Path conventions

Paths are from the repository root.

- `REL` = `scripts/release/`
- `SPEC` = `specs/phase-2/milestone-8-release-v0-1/`
- `SCRATCH` = a directory **outside the repository** for the spike's logs, the demo's authoring scripts
  and the triage table. Nothing from it is ever committed (Milestone 7, research #6).

## Implementation Strategy

### MVP first (US1 and US2)

The smallest thing that is a release is a pipeline that publishes a tested image and a quickstart that
starts it. Do Phase 1, Phase 2, US1 and US2, then **stop and rehearse** (T056) on the merged result of a
pull request that holds only those. The demo, the screenshots and the threat-model update are valuable
but are not needed to prove the pipeline, and a failed rehearsal is cheaper before they are in the same
change. The spec's Definition of Done needs them all before `v0.1.0`, so this is an order of work, not a
smaller release.

### Incremental delivery

1. Phase 1 and 2 → the shared pure code, the spikes' answers, the rulesets.
2. US1 and US2 → the pipeline, the image, the quickstart (MVP; rehearse).
3. US3 → the demo and its checks.
4. US5 and US6 → the proof and the changelog (independent; either order).
5. US4 → the README and the screenshots.
6. US7 → the constitution and the model.
7. Polish → the pull request. Release → after the merge, candidates first.

### Notes

- Every `[MAINTAINER]` task is a decision or a setting that only the owner can make. Nothing in
  Phases 1 to 10 other than T005 changes a repository setting, and nothing before Phase 11 pushes a tag
  or publishes an image.
- A defect found by T032 or T058 is a product change **only** to fix that defect, with a failing test
  first (FR-040). Anything else it finds is an issue.
- Commit after each task or logical group. Do not edit `docs/threat-model/` or `docs/demo/` exports by
  hand, ever; export again.
